# Direct field editing

## iOS: one queue owns the field

Every write the keyboard makes goes through one queue per field (`FieldQueue`). That includes the user's keys, deletes, space-bar cursor pans, word-row and undo edits, live dictation and Soniox revisions, typed lines, the host's text, cleanup and Magic. Nothing else inserts, deletes or moves the cursor, so the queue is the only source of truth for where the cursor is. The one exception is a cursor walk that reads the field for an instruction. It runs only while the queue is paused with nothing in flight and the caret back at the user's cursor.

- **One confirmed op at a time.** The next op goes out only after the field's report confirms the last one. The report must pin the expected cursor in the queue's model of the text, at that place and nowhere else. A report that fits the state before the op as well confirms nothing.
- **Safari timing (measured).** No field puts its caret back after a move. The proxy shows every op at once, before the host has applied it (a move 25–50 ms later, an edit up to about 110 ms later), and ops sent close together can land out of order. An edit lands no sooner than 5 ms after it is sent, a move no sooner than 25 ms. So a move counts only after a report at least 45 ms later, a move follows an insert or delete only 90 ms after it and an edit of the other kind only 110 ms after it, and nothing follows an op that never confirmed before 115 ms. Consecutive inserts (or deletes) at the caret land in order and wait for nothing but the confirmation. A report that goes back to an older state within that transit is the host catching up, not a stale report. An edit sent right after a move can leave the proxy on a stale report; an edit that stays unreported gets a zero-offset move that makes the proxy report afresh.
- **Late reports.** A report of an older state than one already confirmed is lag, never truth: the queue nudges and waits, and believes it only when a fresh report keeps showing it (then the host lost what followed, and those edits are made again). A report at a place no op was going to is the user's tap, even when it still shows older text; after a tap only the user's input goes until the field holds still. The keyboard's own inserts that landed at the tap are taken out again, and text its delete removed there is put back. A tap is placed in known text only on as much agreeing text as finding text again (16 characters, or all the model knows); a report with less (an empty field's) makes the report the new model.
- **Field switches.** Safari gives every field of a page the same document identity, so the keyboard cannot tell a switch from a tap, and a field holding the same words can even pin a place in the old field's model. Work for a field therefore never lands by trust: a jump to a region or an edit counts only when a report pins the caret there. A jump the report shows went nowhere (its whole confirm window long) or stopped short on its way, or one whose report fits several places but not its own, has failed: its work drops once (dictation points to History), it is never tried again, and the model starts over from the report (other spans wait until their text shows again, long and unique). A jump still shown at its start when the user's key waits is such a failure too, never assumed landed (the way back would move the user's caret). Nothing of the keyboard's own starts, and no jump goes out, while the report does not show the model at the caret. After a reseed, the caret goes back the old distance to find the user only when the report still shares text with the old model there, and a way back cut short by the field's edge leaves the user where the caret was.
- **Lanes.** User input goes first, behind at most the op in flight. After the host's transit (115 ms) the op in flight counts as landed and the input goes. Edits come next, then live dictation, with snapshots coalesced to the newest per run.
- **Keys wait for the take (#268).** A key or delete pressed while the take's text already heard is still being typed waits until it is in: typed lines queued at the cursor, then (once the take was stopped) the open region's untyped end, at the floor pace, one grapheme an op. A stopped take holds the keys until it is complete: its final words, still on their way at the stop, go in first too, and so does the item's untyped end when its cleanup came mid-item (the cleanup's changes to words already typed follow the keys). The app marks its snapshots stopped from the stop on (`LiveDictationSnapshot.stopped`, whatever ended the take: mic key, Action Button, bridge), and the keyboard's mic key says so at once. While the take is still spoken a key goes at once, as before. The keys then land in order. The wait scales with the typing still to do (45 ms a grapheme) plus 1 s for the final words, never more than 8 s; after that the keys land and the rest of the take follows them at the caret. A letter key that cut a dictated word short starts a word of its own. A key on the typed-line path finishes the line heard so far first (`DictationTypist.finishLine`). Cursor moves and word-row edits do not wait.
- **Planning at start.** Each item is planned when it starts, against the model as it is then, so queued work rebases onto the user's moves and typing.
- **Jump units.** A change away from the cursor moves there, makes the change, then moves back. No other op goes out meanwhile. User input ends a unit early: the caret goes back first, and the rest is planned again later.
- **Spans (`SpanPlanner`).** The change starts from the minimal grapheme diff. A word that loses and gains at least half its graphemes is replaced whole ("Thursday" to "Friday"; "colour" to "color" stays one deleted letter). Changes up to three unchanged graphemes apart, or in one word, form one span: one jump in and one out. Each span goes in as minimal character edits or as one block delete with its new text typed, whichever the cost estimate (ops at the pace plus settles) says is quicker; a tie keeps the minimal edits. A replacement that would empty a line bounded by a real line break keeps the line's last old grapheme until the new text stands before it, then deletes it: a rich editor puts a placeholder line break into an emptied line, or drops its list item. A single-line field has no such line and takes the block as it is.
- **Pace.** The Mac's curve. Animated text goes one grapheme per op. The gap between typed graphemes spreads the work over about 0.7 s (the unit's own graphemes after its settles, or the whole backlog: the unit, the open region's append and queued edits, whichever is faster), never slower than a calm 30 ms; once 14 or more graphemes are waiting it goes straight to the floor. Nothing waits after the last grapheme. On iOS the calm pace is the floor, the field's confirmation (30 ms; one 33 ms tick, about 45 ms against Safari's timing), so every grapheme goes as soon as Safari confirmed the last. The curve is the Mac's (`SpanPlanner.macPaceMs`, its 5 ms floor included) taken no faster than the iOS floor (`paceMs`); like the Mac, there is no pause between words.
- **Caret into view.** A keyboard cannot scroll a web page, and the page does not follow a caret moved back to the take's end. After a batch of a take's jump units (a cleanup or revision), when the caret is back at the end of the take's own text and nothing else waits, its last grapheme (not whitespace, and never one alone on its line) is deleted and typed again, two confirmed ops, once per batch.
- **No freezing.** A report that does not confirm leads to a resync. The queue re-locates the model around the cursor (unique matches only) or takes the report as the new model, then planning goes on. An edit is dropped only when its text can no longer be placed or the user changed it. Drops are reported to the owner: Magic answers the app, which keeps the original and the rewrite in History, and dictation points the user to the take in History. A dictation region that is out of sight waits.
- **Dictation regions.** A live run types at its region's end. Each take is a run of its own in the app: the mic key (or Action Button) begins it, and so does the bridge's first `dictation-debug-line` or `-tail` after a `dictation-debug-stop`. A take that begins while the previous run still ends (its stop waits for the last words and their cleanup) waits until that run is complete, so none of its words join the old run; stops end runs in take order, and a later stop never cancels an earlier take's end. Every take starts its first region at the user's caret, wherever they put it; text typed by hand between takes (Enter, "- ", words) stays in front of it, and nothing of an earlier take pulls new words elsewhere. A key or a cursor move closes the region, and a word cut short by a key is finished first. Later raw words start a new region at the user's cursor, also after the user edited the take's own text. A region whose revision cannot land drops once, not once per version. A take that typed nothing yet follows the user into another field (the keyboard's field changed); one that typed something stops there, drops once, and its later versions are ignored. A revision or cleanup belongs to the run's own text: its changes map onto the regions where they are, and text it adds at the end of the take (punctuation, a trailing word) goes at the end of the run's last region, never at the cursor. A segment the keyboard never saw is new speech, also after the take ended (a run that goes on after a stop): it starts at the caret. Snapshots that bring new speech are never coalesced away, and a cleanup that joins unseen speech with known words (the link skipped the raw version) shows the unseen part raw. Regions split by the user's typing or moves are separate pieces: where a snapshot changes the joint between two pieces (", " for a space, "," for ".", " and "), the joint belongs to neither, so no joiner lands at a line's start or end; a joint that stays is left alone. The keyboard reports where the pieces start (`LiveDictationAck.pieces`), and the app cleans each piece on its own and skips the whole-take pass. Pieces cleaned apart (their words in different segments) keep their own sentence ends; only a changed joint inside one cleanup unit is a joiner. A report that comes after the stop already sent a unit spanning the pieces to cleanup cuts that unit: its parts are cleaned again and the joined result never lands. A finished take keeps its regions until its cleanup came (for the last four takes), so a cleanup that arrives after the next take started still lands in its own text; a later version of a take no longer kept is ignored (it is in History), never typed at the caret. In a region the user edited, each change touching a word the user changed is dropped; every other change still lands (`FieldMerge`), as minimal character edits that leave the user's characters alone.
- **Instructions (Magic).** A read for an instruction waits (bounded) until the queue's own writes have landed, and marks the model (`markRead`). The edit is placed through every change since that read: a user change inside its scope cancels it; the keyboard's own changes there (a cleanup that arrived meanwhile) never do, and are merged into the result where Magic's change does not touch them.

Internal builds journal every queue event with full text (`EditJournal`; see `scripts/device/README.md`). A pulled journal replays against the queue in a test.

## macOS

One queue per field (`MacFieldQueue`) makes every change: live words and their revisions, cleanup, typed lines, Magic and its undo, and the panel's final typed insert. Nothing else writes to the field.

- **One op in flight.** Each op is planned just before it goes out, against the field as last read: select the spot, replace, then read back the text and caret before the next op.
- **Minimal diff, typed.** Only the differing characters change, one grapheme per op at the typewriter pace. Reduce Motion, the Typewriter setting off, or a flush (Magic reading the field) sends each change whole. A change away from the user's caret is a jump unit: the caret goes back to where the user expects it.
- **Rebase, never freeze.** The user's typing and clicks show on the next read. A key or click closes the open dictation region, and later words start a new region at the user's caret. Regions are found again at their place or uniquely elsewhere, and pending work is replanned there. Only work whose text the user changed, or that cannot be placed, is dropped; the take or result stays in History and goes to the clipboard. Words after a region the user changed start a new region at the caret.
- **Focus by editor.** A take binds the element focused when it starts and types at its caret. Chromium recreates a web field's element when the page rewrites its DOM (Enter, a new list line, a re-render) and moves focus between nested editable elements, so the bound element can stop reading as focused while the user types on in the same editor. Then the queue binds the focused element if it is the same editor: the element itself, one inside it or its editable root, one under the same editable root, or a fresh element in its place (same window, role, DOM id and classes, x and width). While the take has typed nothing, any editable text field of the same app is bound, and the take starts at its caret. Typed work moves by the one shift under which all of it shows. Another app or another field after typing waits up to 3 s; then each take drops once, whole, with one message, and its later versions are ignored. The same editor in focus is never a drop: if it stops reading (below), the take goes on in the panel.
- **Reading web editors (`AXFieldReader`).** Chromium exposes an editor's text in two spaces. Its value and character count have a line break between every two lines, but its selection, `AXStringForRange` and text markers leave out the break between two adjacent non-empty lines: a tight Markdown list in CodeMirror, `<li>` or `<p>` blocks in a contenteditable. Reading the whole count then fails. Such an editor reads as its value, with the selection mapped into it. Where one selection offset stands for the end of a line and the start of the next, the text marker before the caret decides. A focused element that exposes nothing reads through its editable root (`AXEditableAncestor`, `AXHighestEditableAncestor`). An editor that reads neither way dictates through the panel from the start.
- **Unreadable mid-take.** When the bound editor has focus but stops reading for 0.6 s, its pending dictation goes on in the panel for the rest of the take. What was typed live stays; the panel shows the rest as it grows and is cleaned, and types it once at the end with synthetic keys. Nothing is dropped and no notice shows.
- **Keystroke fields.** Chromium web content (Chrome, Edge, their installed web apps, Electron) exposes its text once Legato reads the application's role, but ignores Accessibility text writes. The queue edits it live with synthetic keys, one in flight: Backspace to delete, one grapheme per Unicode key to type. Line breaks and tabs are pasted, never Return or Tab keys, and the clipboard comes back.
- **Value first.** An edit key counts when the field's value shows it: the expected text at its place, what followed still after it, and the length. Chromium reads an empty last line as a placeholder line break that goes when the line gets text, so one trailing line break more or less at the end of the field is the same text. Its caret can report late after a key on an empty line or at a block start: a key whose text shows is never sent again; the queue waits for the caret, and if the caret still reads as before the key, one arrow makes the field report afresh before anything else goes out. A key whose text does not show is not sent again until it shows or a second has passed.
- **Jumps.** The caret goes straight to a change and back; each jump is one verified step before the edit. Where the field honours an Accessibility caret set, the queue uses it, after one arrow proved that the real caret followed (Chromium may report a set it did not make). Otherwise it hops: Command+Up/Down to the field's start or end and Command+Left/Right to the caret's own line start or end when the target is there or a short arrow run from it, Option+Left/Right while the next word boundary is not past the target, then runs of up to eight plain arrows. A jump that lands off its prediction is corrected from where the field reports the caret, within four correction rounds, then arrows only; a hop that missed is not repeated toward the same target. What works (the caret set, and each hop's hits and misses) is remembered per field across takes.
- **Keystroke planning.** As on iOS, a word that changes by half or more is retyped whole, changes a few characters apart merge into one span, and each span takes minimal edits or a block delete and retype, whichever costs less. A caret move costs one key per grapheme up to the price of a jump, so far changes stay minimal. A small change types at a calm 30 ms per key and spreads a larger one over about 0.7 s; once 14 or more graphemes are waiting (typing is behind speech, about 15 characters a second) every key goes at the 5 ms floor, 3 ms in an Accessibility-writable field. A run of up to 4 typed graphemes (8 when behind) is verified by the caret alone, one read per key, and the run's text, tail and length by one read after its last key; each key still passes the guards below, and a move, a Backspace or a failed key ends the run. Moves and edits settle briefly between each other.
- **Key guards.** Before every key and caret set: the bound element is focused in the frontmost app, no real key or click since the key was planned, no modifier held (keys only), and the selection is still where it was read. Hops press the left-hand Option or Command around their arrow; Right Option and Right Command stay Legato's shortcuts. A failed guard sends nothing; the queue reads again and replans. A held modifier (push-to-talk) only pauses it. Every synthetic key-down has its key-up, and a sequence goes out whole or not at all.
- **Pill controls and history.** A take typing live into its field shows only a compact listening state in the notch pill, with Magic (the Magic hotkey), Undo and Redo. Undo takes Legato's last finished change (a take, with its cleanup, or a Magic edit) back through the queue as minimal edits; Redo puts the last undone change back. Both are disabled when there is nothing to do, and new dictation or a new edit ends the redo. The pill never becomes key or main, and its area is excluded from the real-input count, so a click on it neither moves focus nor trips the key guards.
- **Panel mode.** Unreadable fields show the take in the notch panel; Settings can choose the panel for every field ("Always dictate in the panel, insert when done", `dictation.panel` = `always`). The panel shows the take as it grows and is cleaned, and nothing touches the field until the take is final. A field the queue can edit (Accessibility or verified keys) then gets the text once through the queue, as one insert at the user's caret typed at the fast end of the pace. An unreadable field gets one typed insert with synthetic keys at the end, while the same app is in front and no real key was pressed.

Debug and internal builds journal every queue event with full text in `~/Library/Caches/<bundle id>/edit-journal.jsonl`.

## Recovery

Before applying a Magic rewrite, Legato saves the original and generated result together in History. The same entry records whether application succeeded, was refused or could not be confirmed. A recovery-save failure prevents the edit from being sent.

History copies the generated result by default. Its context menu offers Copy original for a rewrite. Both versions remain available after a read or write failure, without another successful field walk. Undo is offered only when a known resulting scope can be verified. Explicit instruction retries use a fresh identity and revoke the previous attempt.

## Limits and verification

A keyboard extension cannot obtain the complete text or absolute caret position in every host. Structural boundaries, missing selection information, stale browser proxy windows and text typed by another keyboard can make an edit unverifiable. Such cases resync or drop with a specific status instead of writing at a guessed position.

The package checks cover the queue's contracts (minimal flips, the bound on user input, rebasing, unit integrity, drops), a Markdown list typed take by take ("- ", dictate, cleanup, Enter, "- ", ..., with cleanups on time and late), a characters-per-second report under Safari's timing (`LEGATO_PACE_REPORT=1`) and a seeded stress test. The stress test also switches fields under pending work (an empty field, one holding a copy of the old field's text, other text) and runs list sessions in one run ("\n- " between items, takes stopped and continued, cleanups joining the items early, mid-list or at the end). Its fake field lags, shows short windows, echoes Safari's block boundary, moves emoji as one unit and reproduces the measured Safari timing. On macOS a seeded stress test drives the queue against a fake Accessibility field with lagging reads, user typing and clicks, revisions, cleanup and Magic, and against a fake keystroke field whose keys lag, land late, drop and meet focus blips; it can show an empty last line as a placeholder, report the caret late after a key at a line start, take, ignore, delay or only pretend to take caret sets, land word hops a few characters off and wrap lines. In half the sessions the fake recreates its element or moves focus into the caret line's nested element, sometimes before the first word. Two more modes play the keystroke sessions in a tight list read like Chromium's (hidden line breaks, a focused element that sometimes exposes nothing so reads go through its root), and with the whole editor unreadable for a while or for good, where a take must go on in the panel and the field's words plus the panel's rest must be the take's, each once. A test replays a real Edge journal where the first key on an empty last line was typed twice, another the Edge take whose element was recreated after Enter and "- " (it used to drop every version as focusLost), and one types a list take by take with Enter and "- " typed by hand between them. `LEGATO_STRESS_RUNS` sets a long local run and `LEGATO_STRESS_SEED` replays one seed. Native acceptance uses the real Safari fields and keyboard extension on iOS, and the running desktop app against browser fields on macOS. In-process text fixtures do not establish browser compatibility. Offline speech and instruction fixtures establish field behavior, not recognition or model quality.

# Direct field editing

## iOS: one queue owns the field

Every write the keyboard makes goes through one queue per field (`FieldQueue`). That includes the user's keys, deletes, space-bar cursor pans, word-row and undo edits, live dictation and Soniox revisions, typed lines, the host's text, cleanup and Magic. Nothing else inserts, deletes or moves the cursor, so the queue is the only source of truth for where the cursor is. The one exception is a cursor walk that reads the field for an instruction. It runs only while the queue is paused with nothing in flight and the caret back at the user's cursor.

- **One confirmed op at a time.** The next op goes out only after the field's report confirms the last one. The report must pin the expected cursor in the queue's model of the text, at that place and nowhere else. A report that fits the state before the op as well confirms nothing.
- **Safari timing (measured).** No field puts its caret back after a move. The proxy shows every op at once, before the host has applied it (a move 25–50 ms later, an edit up to about 110 ms later), and ops sent close together can land out of order. So a move counts only after a report at least 60 ms later, an op of another kind follows an insert or delete only 115 ms after it, and nothing follows an op that never confirmed before 150 ms. A report that goes back to an older state within that transit is the host catching up, not a stale report. An edit sent right after a move can leave the proxy on a stale report; an edit that stays unreported gets a zero-offset move that makes the proxy report afresh.
- **Late reports.** A report of an older state than one already confirmed is lag, never truth: the queue nudges and waits, and believes it only when a fresh report keeps showing it (then the host lost what followed, and those edits are made again). A report at a place no op was going to is the user's tap, even when it still shows older text; after a tap only the user's input goes until the field holds still. The keyboard's own inserts that landed at the tap are taken out again, and text its delete removed there is put back.
- **Lanes.** User input goes first, behind at most the op in flight. After about 150 ms the op in flight counts as landed and the input goes. Edits come next, then live dictation, with snapshots coalesced to the newest per run.
- **Planning at start.** Each item is planned when it starts, against the model as it is then, so queued work rebases onto the user's moves and typing.
- **Jump units.** A change away from the cursor moves there, makes the change, then moves back. No other op goes out meanwhile. User input ends a unit early: the caret goes back first, and the rest is planned again later.
- **Spans (`SpanPlanner`).** The change starts from the minimal grapheme diff. A word that loses and gains at least half its graphemes is replaced whole ("Thursday" to "Friday"; "colour" to "color" stays one deleted letter). Changes up to three unchanged graphemes apart, or in one word, form one span: one jump in and one out. Each span goes in as minimal character edits or as one block delete with its new text typed, whichever the cost estimate (ops at the pace plus settles) says is quicker; a tie keeps the minimal edits.
- **Pace.** Animated text goes one grapheme per op. The gap between typed graphemes spreads the work over about 1.2 s: the unit's own graphemes after its settles, or the whole backlog (the unit, the open region's append and queued edits), whichever is faster. It is never slower than a calm 65 ms, nor faster than the field's confirmation (30 ms; in practice one 33 ms tick, about 45 ms against Safari's timing).
- **No freezing.** A report that does not confirm leads to a resync. The queue re-locates the model around the cursor (unique matches only) or takes the report as the new model, then planning goes on. An edit is dropped only when its text can no longer be placed or the user changed it. Drops are reported to the owner: Magic answers the app, which keeps the original and the rewrite in History, and dictation points the user to the take in History. A dictation region that is out of sight waits.
- **Dictation regions.** A live run types at its region's end. A key or a cursor move closes the region, and a word cut short by a key is finished first. Later raw words start a new region at the user's cursor. A revision or cleanup belongs to the run's own text: its changes map onto the regions where they are, and text it adds at the end of the take (punctuation, a trailing word) goes at the end of the run's last region, never at the cursor. In a region the user edited, each change touching a word the user changed is dropped; every other change still lands (`FieldMerge`), as minimal character edits that leave the user's characters alone.
- **Instructions (Magic).** A read for an instruction waits (bounded) until the queue's own writes have landed, and marks the model (`markRead`). The edit is placed through every change since that read: a user change inside its scope cancels it; the keyboard's own changes there (a cleanup that arrived meanwhile) never do, and are merged into the result where Magic's change does not touch them.

Internal builds journal every queue event with full text (`EditJournal`; see `scripts/device/README.md`). A pulled journal replays against the queue in a test.

## macOS

One queue per field (`MacFieldQueue`) makes every change: live words and their revisions, cleanup, typed lines, Magic and its undo, and the panel's final typed insert. Nothing else writes to the field.

- **One op in flight.** Each op is planned just before it goes out, against the field as last read: select the spot, replace, then read back the text and caret before the next op.
- **Minimal diff, typed.** Only the differing characters change, one grapheme per op at the typewriter pace. Reduce Motion, the Typewriter setting off, or a flush (Magic reading the field) sends each change whole. A change away from the user's caret is a jump unit: the caret goes back to where the user expects it.
- **Rebase, never freeze.** The user's typing and clicks show on the next read. A key or click closes the open dictation region, and later words start a new region at the user's caret. Regions are found again at their place or uniquely elsewhere, and pending work is replanned there. Only work whose text the user changed, or that cannot be placed, is dropped; the take or result stays in History and goes to the clipboard.
- **Keystroke fields.** Chromium web content (Chrome, Edge, their installed web apps, Electron) exposes its text once Legato reads the application's role, but ignores Accessibility text writes. The queue edits it live with synthetic keys, one in flight, each confirmed by reading the text and selection back: Left/Right arrows without modifiers to move, Backspace to delete, one grapheme per Unicode key to type. A key that does not read back is not sent again until it shows or a second has passed. Line breaks and tabs are pasted, never Return or Tab keys, and the clipboard comes back.
- **Keystroke planning.** As on iOS, a word that changes by half or more is retyped whole, changes a few characters apart merge into one span, and each span takes minimal edits or a block delete and retype, whichever costs less. A change aims at about 1.2 s; typing speeds up with the backlog, still one grapheme per key. Moves and edits settle briefly between each other.
- **Key guards.** Before every key: the bound element is focused in the frontmost app, no real key or click since the key was planned, no modifier held, and the selection is still where it was read. A failed guard sends nothing; the queue reads again and replans. A held modifier (push-to-talk) only pauses it. Every synthetic key-down has its key-up, and a sequence goes out whole or not at all.
- **Panel mode.** Unreadable fields show the take in the notch panel. The queue's only op there is one typed insert with synthetic keys at the end, while the same app is in front and no real key was pressed.

Debug and internal builds journal every queue event with full text in `~/Library/Caches/<bundle id>/edit-journal.jsonl`.

## Recovery

Before applying a Magic rewrite, Legato saves the original and generated result together in History. The same entry records whether application succeeded, was refused or could not be confirmed. A recovery-save failure prevents the edit from being sent.

History copies the generated result by default. Its context menu offers Copy original for a rewrite. Both versions remain available after a read or write failure, without another successful field walk. Undo is offered only when a known resulting scope can be verified. Explicit instruction retries use a fresh identity and revoke the previous attempt.

## Limits and verification

A keyboard extension cannot obtain the complete text or absolute caret position in every host. Structural boundaries, missing selection information, stale browser proxy windows and text typed by another keyboard can make an edit unverifiable. Such cases resync or drop with a specific status instead of writing at a guessed position.

The package checks cover the queue's contracts (minimal flips, the bound on user input, rebasing, unit integrity, drops) and a seeded stress test. Its fake field lags, shows short windows, echoes Safari's block boundary, moves emoji as one unit and reproduces the measured Safari timing. On macOS a seeded stress test drives the queue against a fake Accessibility field with lagging reads, user typing and clicks, revisions, cleanup and Magic, and against a fake keystroke field whose keys lag, land late, drop and meet focus blips. `LEGATO_STRESS_RUNS` sets a long local run and `LEGATO_STRESS_SEED` replays one seed. Native acceptance uses the real Safari fields and keyboard extension on iOS, and the running desktop app against browser fields on macOS. In-process text fixtures do not establish browser compatibility. Offline speech and instruction fixtures establish field behavior, not recognition or model quality.

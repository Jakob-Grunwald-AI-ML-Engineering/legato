# Selected model resources

Legato prepares selected speech and cleanup resources at foreground startup or first use and retains them across dictations and microphone expiry. Ending a microphone lease ends capture; it does not unload selected weights. The regular keyboard and app controls use this path without an Action Button prerequisite. Cold preparation is expected after process restart, first installation, model changes or resource reclamation, not after ordinary dictation stops or microphone expiry. There is no idle model-unload timer, periodic dummy inference, or audio capture solely to retain models.

Downloadable cleanup choices use Core ML: Qwen3 0.6B, Qwen3 1.7B and Gemma 3 1B. Apple Foundation Models remains an explicit built-in choice. Downloadable speech models already use Core ML through FluidAudio; Apple Speech remains a separate system choice. Production app dependencies do not reach the legacy MLX library, which remains isolated for tooling and historical tests. Unsupported old backend values reset to the built-in default and unsupported cleanup IDs are cleared; old model families are not mapped forward. Existing weights and unrelated settings are not deleted.

Each selected model has one resource identity shared across dictation, Refine and meeting summaries. The owner retains the union of their requests, while each operation awaits only its required subset. With automatic cleanup disabled, dictation awaits speech alone while the Refine model can prepare independently. A missing or failing meeting-only model cannot block dictation using Foundation Models. A model stays retained while any role requests it or an operation holds a lease. Meeting preference changes reconcile retention without canceling dictation admission.

When an installed selected Core ML cleanup model is preparing and Apple Foundation Models is available, dictation temporarily uses Foundation Models without changing the selected model. Dictation admission awaits selected speech and the effective cleanup resource rather than the pending local cleanup load. Keyboard microphone-only arming joins engine selection, validates microphone permission and installed assets, and activates the real capture lease without awaiting downloadable speech weights. Nemotron and Parakeet EOU provide their existing fixed capture format without creating a recognizer. Actual dictation still awaits the selected recognizer; Apple Speech retains its existing format-preparation path. The ready screen permits returning to the keyboard and distinguishes pending speech preparation from a ready microphone. Each dictation retains one resolved backend through its rolling and final cleanup passes; newly ready Core ML takes over on a subsequent dictation. The selected speech engine is unchanged, so its cold preparation can still delay recognition after the microphone has armed. Cold engine resolution is published before URL handling; cancelled, refused or duplicate idle requests cannot leave a progress screen without an active activation.

A keyboard Start awaiting selected speech publishes cancellable preparation immediately, separately from listening. Accepted means the host owns the request, not that recording has started. A second microphone tap stops that pending request; it cannot manufacture another foreground hop or leave a request that captures later. Cancellation leaves shared model preparation retained. Terminal results remain available for every accepted Start ID, including duplicates, so the keyboard does not need to observe a transient preparing state. A missing or stale host falls back after heartbeat freshness expires; a live preparation has no fixed total timeout. A finite microphone lease keeps its configured expiry; loss of the lease during admission invalidates the pending request rather than silently starting fresh capture later.

Foreground operations may start or join preparation; background operations reuse or join an admitted preparation rather than begin cold loading. Missing local weights are never published as ready. A canceled waiter returns promptly without canceling shared preparation or starting capture later. Stop bypasses preparation. Memory pressure revokes readiness and joins native settlement before releasing ownership; subsequent foreground admission prepares resources again. Process termination and OS memory decisions remain outside application control. Independent asynchronous preparation is not an unlimited iOS execution grant: preparation can pause when iOS suspends an idle app. Returning to normal keyboard dictation uses the existing microphone background execution path; automatic preparation does not add a continued-processing task or signing entitlement.

Meeting summaries acquire their resource lease inside the scheduler lane and hold it through all transcript chunks and merges. Cold or missing resources defer an automatic summary without marking the meeting finished or consuming unrelated post-pass retry attempts. Deferred model work leaves the polling lane until foreground recovery or settings reconciliation requeues it. Explicit Claude summaries keep their separate consent and API path.

Selected FluidAudio resources are pinned independently of incidental meeting models. Per-recording decoding state is fresh while selected model weights are reused. Existing per-model CPU/Neural Engine policies remain intact, including CPU-only Core ML audio processing where required. Apple Speech requests `SpeechAnalyzer.Options.ModelRetention.processLifetime` and creates fresh per-run analyzers; the Speech framework owns its cache. Foundation Models retains a prewarm session and creates fresh sessions for responses. Its API does not guarantee physical residency.

Core ML installers accept only bundled, pinned manifests with exact file inventories and SHA256 verification. Receipts and file stamps guard state reads; initial runtime preparation verifies full hashes again. Incomplete, changed and symlinked artifacts cannot become ready. Weights are downloaded on an explicit model pick and are not bundled with the app. Gemma's governing terms, restrictions and notice are available offline before its download.

All three remain selectable by the user's explicit decision after reviewing their measured limitations. Qwen 0.6B is marked experimental because it can change numbers and times incorrectly. Gemma is marked experimental because preparation can fail on some devices. A genuine Core ML preparation failure appears in Cleanup settings with an explicit Retry action. When Foundation Models is available, dictation continues using it while the chosen local model remains selected. Automatic reconciliation does not repeatedly retry a failed load. Normal preparation is shown as status rather than an error. If Foundation Models is unavailable, admission retains the selected-model preparation path and reports failures truthfully. Refine and meeting summaries retain their explicit selected-model policy. This startup bridge does not retry generation failures, timeouts or guard rejection on another backend. The new 0.6B LUT8 checkpoint is distinct from the historical local LUT6 derivative whose failed parity evidence remains unchanged.

Native Core ML ownership spans prediction settlement, including cancellation and release. Prompt rendering must match each checkpoint's canonical Qwen or Gemma template. The full production instructions/examples, output reservation and EOS-only completion policy remain enforced. Context overflow, incomplete generation, timeouts, stage failures and guard rejection preserve input through the production pipeline. Core ML defaults to an eight-second cleanup budget and Foundation Models to four seconds unless the user explicitly chose a limit. The numeric-value guard limitation remains tracked in #54; it does not catch every incorrect model output.

[Current native checkpoint evidence](../validation/64-coreml-catalog-native.json) records three short public inputs on an Apple M1 Pro with 32 GB RAM at runtime commit `c99fad5`. Qwen 1.7B passed 3/3 exact-reference checks in 6.66–7.21 seconds and passed a short meeting-summary fact check. Its separate process took 230.78 seconds to prepare. Qwen 0.6B passed 0/3: a wrong time, a casing failure and a timeout; the incorrect time passed the guard. Gemma failed loading before inference. Independent load diagnostics reproduced its CPU/Neural Engine compiler failure while CPU-only `infer` and `prefill` loads succeeded; those diagnostic loads do not establish inference quality or a production fallback.

These measurements exercise the runtime checkpoint, not the later app admission changes. They do not establish phone behavior, physical Neural Engine placement, sustained energy/thermal behavior or residency after process loss. Two Qwen 0.6B calls exceeded 8000 ms while reporting no timeout; that observed scheduling behavior is retained in the evidence. Earlier [native measurements](../validation/58-native-coreml.json) remain a separate checkpoint. Device and thermal validation remains in #58; broader settings simplification remains in #62.
